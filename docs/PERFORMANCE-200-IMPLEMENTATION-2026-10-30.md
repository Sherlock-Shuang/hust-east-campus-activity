# 200 人活动性能优化与验收

本轮从生产分支 `5f66278` 建立隔离工作区，继续上一轮性能优化。保留地图、资源、角色、碰撞、门洞、速度、蛛丝操作、活动身份和原作品；不向正式场次写测试观众，不调用真实模型。

## 已实现

### 活动连接与数据库

同一个数据库 adapter 对应一个 SSE 调度器，取代每条连接的轮询循环。仍按约 1.5 秒周期检查状态；新订阅立即取得完整快照。每 15 秒的租约更新按最多 200 个 ID 合并为一条 SQL，保留每流独立的 240 秒到期、取消和慢消费者隔离。最后一个订阅退出后停止共享调度。

授权、入场、观众事件持久化和主持人版本检查仍走原实时数据库逻辑。取消后的租约不能被在途 UPDATE 重新创建。失败会关闭受影响连接，由客户端重连读取最新状态。

**批量 UPDATE 减少 SQL 语句、网络往返和定时器，不等于减少按行计费。**同实例 200 条连接每分钟只需 4 条续租 UPDATE，但仍续租 800 行。多个 Vercel 实例之间没有新增共享消息服务；实例越分散，可合并的收益越小。

### 客户端与恢复

首次 SSE 打开不再重复 GET 全场状态；单条流显式管理重连，正常断线随机等待 500–1000 ms，持续失败指数退避，最多随机 15–30 秒。恢复、校时合并并错峰；旧流迟到事件不会改写新连接。保持后台接收主持状态。

通过真实可见性事件记录计时边界，即使隐藏期间没有任何 RAF，回到游戏也不会补执行 100 ms 移动。正常前台长帧和现有物理步长保护保持。首次校时后，普通 RTT 修正通过 0.9–1.1 倍速渐进收敛，不让活动时间倒退；检测到休眠停钟则向服务端重新校准，丢弃跨睡眠的旧回复。本机墙钟仅作唤醒提示，不作活动时间依据。时间边界与网络验证见 [客户端说明](PERFORMANCE-200-CLIENT.md)。

### 模型请求过载保护

旧代理在等待共享配额时未先占用本地并发位，200 个突发请求可能全部通过“最多 8 个”的检查。本轮修复这一竞态，两个聊天作品共用每实例 8 个执行位、16 个等候位；每位观众最多占 1 个等候位，最长等候 12 秒。满队列或等候超时返回明确的 429 与 Retry-After，不做自动重试风暴。

正文校验在配额前完成；进入执行位才预留配额，未执行的等待取消/超时不消耗额度。断开、流错误和超时释放执行位。已经发起原子数据库预留后再取消，仍可能占用额度；不能声称取消必然退款。

全场每天 500 次及个人限制保持，没有提高花费上限。本轮改动是可靠限制与有限等待，**不是让 200 人的 AI 请求同时执行，也不是吞吐提升**。模型测试均使用 mock。

## 200 人真实 HTTP/SSE 对照

Node 24.22.1，同一 Mac、同一压测脚本，两个服务 handler、两个 libSQL 客户端共享新建本地 SQLite。旧版活动 API 与生产 `5f66278` 相同；脚本记录实际实现 SHA-256。旧、新顺序各运行 300 秒，各 3,579 次 API，200 个注册请求同时发起，随后并发连接、事件和心跳。

| 指标 | 旧版 | 本轮 |
| --- | ---: | ---: |
| 数据库语句（收尾清理前） | 16,758 | 12,696（减少 24.24%） |
| 连接续租 UPDATE | 4,030 | 42（减少 98.96%） |
| 主持广播 P95 | 1,105.63 ms | 1,281.97 ms |
| 探索事件 P95 | 769.20 ms | 538.85 ms |
| 请求错误／重试 | 0 / 0 | 0 / 0 |
| 自然轮换／主动重连 | 190 / 30 | 190 / 30 |
| 结束后的连接租约 | 0 | 0 |

两轮每次主持人修改均覆盖当时应接收的全部观众；身份、多标签、重复到访、加载失败、已打开及返回统计正确。广播仍在原 3 秒目标内，并未宣称广播延迟降低。查询量包括合并续租之外的认证、事件和状态查询；本次各一轮，不将单次耗时差外推为普遍提升。

JSON 记录先于最终连接清理，终端 completed 行会额外计入 200 条租约删除及一次检查；比较使用两份 JSON 的相同口径。

原始结果：`artifacts/capacity-200/baseline-200-300s.json`、`optimized-200-300s.json`。

## 分散实例与延迟补测

另用同一脚本顺序运行旧/新各一次：200 人、16 个独立 handler/数据库 adapter，每次 SQL execute 人工延后 40 ms，90 秒采样，含收尾各约 91.5 秒。各 1,977 次 API、20 次主动重连，零错误/重试，全部指令覆盖，最终租约 0。

| 指标 | 旧版 | 本轮 |
| --- | ---: | ---: |
| 数据库语句 | 9,295 | 8,013（减少 13.79%） |
| 续租 UPDATE | 1,210 | 90（减少 92.56%） |
| 主持广播 P95 | 1,437.69 ms | 1,346.67 ms |

实例分散后收益变小，符合每实例合并的边界。这是人工延迟模型，未模拟远程吞吐上限、数据库尾延迟或 Vercel 调度；没有覆盖该组的 240 秒轮换。不能据此声称已完成公网 200 人验收。报告：`artifacts/capacity-200/*-200-16instances-40ms.json`。

## 复测

```sh
node scripts/soak-activity-capacity.mjs --seconds 300 --audiences 200
node scripts/soak-activity-capacity.mjs --seconds 90 --audiences 200 --instances 16 --db-latency-ms 40 --reconnect-ms 30000
node scripts/verify-live-client-browser.mjs
```

容量脚本不会读取 `.env`，仅创建临时本地数据库；退出关闭服务并删除数据库。人数参数严格验证，不会把 200 静默裁成 100。`--runtime-root` 允许读取另一个本地基线源码；`--db-latency-ms` 仅为每次 execute 注入合成延迟，不代表真实远程数据库。

## 边界

- 本地 200 人验证不是 200 台设备渲染、CDN 同时下载、现场 Wi-Fi 或公网 Turso 压测。仍需隔离的远程数据库长测及现场无代理访问验证。
- 这一轮没有重新压缩模型、改变画质或提升前台 FPS 的实测结论；上轮资源、LOD、实例驻留和渲染预算继续生效。
- AI 全场 500 次预算不适合让 200 人持续自由聊天；需按活动轮次和费用预算另行配置，不能靠本地排队消除该限制。
- 原有接近 2,500 连接／5,000 观众记录时的 COUNT 后 INSERT 非原子入场边界不在本轮 200 人验证范围内，不将这些数值作为保证承载量。

沿用 GitHub → Vercel 部署及原数据库，不更换平台、不迁移活动数据。回退基线为 `5f66278`。
