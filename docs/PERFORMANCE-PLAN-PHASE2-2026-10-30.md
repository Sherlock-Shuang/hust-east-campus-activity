实施已开展并完成本轮交付；实际改动、测量结果和仍待真机验证的边界见 [第二阶段实施与验收](PERFORMANCE-PHASE2-IMPLEMENTATION-2026-10-30.md)。下文保留制定时的基线和试验目标，不将目标数字当作已取得的收益。

整理日期：2026-10-30。基于上一轮生产版本 `a120315be9cc1791c339da48b5208b14a061146f` 的验收记录，并重新只读核对当前源码。本次只更新方案，没有修改游戏、重跑压测或发布版本。主目录存在独有的活动层改动，并非生产提交的完整镜像；下一次实施仍须从最新发布提交建立隔离工作区，再增量合并。

下一阶段重点是：让普通手机和集显电脑少画、少驻留、少等待，同时保留完整校园、真实入口和现有移动规则。最高优先级是补测量口径、修复画质预算漏接、给室外洪水分档；随后推进出生区先可玩、街区细节卸载和作品轻量资产。

**2．统一验收口径：先区分五种成本**

| 成本 | 要记录什么 | 避免误判 |
| --- | --- | --- |
| 下载 | 冷/热缓存传输字节、首字节、资源并发、请求取消 | GLB 原文件大小、仓库 gzip 分片大小、实际 Brotli 流量分开 |
| CPU | 构建阶段、输入/物理、可见性、人物、事件、长任务 | `renderer.render()` 在 CPU 上的耗时不是 GPU 用时 |
| GPU | 主画面、阴影、倒影、透明水体的分项对照；支持时使用有效 GPU timer | 无扩展或发生 disjoint 时不输出伪精确 GPU 数值；不使用阻塞等待测量 |
| 内存 | JS 堆、独立几何属性字节、纹理/渲染目标估算、媒体和引擎实例 | 对象数量不等于显存；共享 Buffer/材质不得重复计数 |
| 服务 | SQL 类型/耗时、函数实例、连接轮换、主持命令接收、持久化 | 100 条连接测试不等于 100 台设备渲染或同时下载作品 |

建立固定机位和输入回放版本，记录提交、资源 manifest 哈希、设备型号、系统、浏览器、视口、DPR、画质、刷新率和网络。性能 A/B 使用固定档；自动档另跑并记录每次升降档，避免通过自动降画质制造不公平的对比。

拟定发布目标如下，均为待验证目标，不能预先填写“已达标”：

| 场景 | 第一轮目标 |
| --- | --- |
| 普通电脑，均衡档 | 目标 60 FPS，P95 帧间隔 ≤22 ms |
| 中端手机/旧集显，流畅档 | 稳定 30 FPS，P95 ≤40 ms；30 分钟后仍可操作 |
| 预热后的连续路线 | >100 ms 长帧 ≤2 次/分钟；首次作品载入单列 |
| 首次可操作 | 相对校准后的同设备基线降低 25–30%；不得以显示加载页计可玩 |
| 热稳定 | 后 5 分钟同路线 P95 相对冷机预热段恶化不超过约 20%，并仍满足本档目标 |
| 返回作品 | 同地点预热后后 5 轮资源形成平台，不按轮次持续增长；无重复音频、监听和输入残留 |
| 现场控制 | 健康网络中公告/入口/暂停应用 P95 ≤3 秒；掉线恢复后采用最新 revision |

内存平台以同设备、同等待时间、同缓存条件比较；浏览器缓存/垃圾回收带来的短时波动单列。能取得可靠进程或堆数据时，先以“后 5 轮平台比预热平台高不超过约 10%”作为调查阈值，不把这个阈值当所有浏览器的硬性显存上限。

**3．P0-1：补齐长时报告和真正的首帧、首个可操作画面**

涉及 `src/frame-metrics.js`、`src/runtime-diagnostics.js`、`src/survey.js`、`src/c118-viewer.js`。

- 保留现有 1,800 帧滚动窗口，新增按分钟汇总与整个测试会话的有界直方图。1,800 帧在 120/60/30 FPS 时只覆盖约 15/30/60 秒，不能代表半小时。每分钟输出 P50/P95/P99、长帧、实际绘制率、CPU 和质量档。
- 区分 RAF 回调次数与实际渲染次数。现有 `frameRate` 是回调窗口统计；连续渲染分布另有样本条件。主动限帧、暂停和后台不能被当作卡顿，也不能算高 FPS。
- 拆开数据下载、基础世界构建、出生区可见、首帧呈现、首次输入导致可见位移、远区细节完成。首次渲染返回后还需下一呈现周期证据，不直接以构造函数结束时间代替。
- 诊断模式中分项采样阴影/倒影/主画面，避免只读最后一次 `renderer.info`；生产常规开销保持低。对长任务、错误、恢复和作品切换加时间标记。
- 对统计本身做开/关对照，诊断关闭时不逐帧分配大数组、不保留无限历史、不上传身份。

交付：一个可重放路线清单、每设备冷/热各 3 次启动报告、一份 30 分钟报告。先完成本项，再用后面各项的百分比验收。Three.js 的多 pass 统计需要明确 `info.autoReset` 与重置时机，不能直接将最终 render 的值视为完整帧预算。[官方说明](https://threejs.org/docs/pages/WebGLRenderer.html)

**4．P0-2：先补画质预算漏接，再改大型结构**

具体发现：`src/commute-scene.js` 的 `vegetation.update(lastCamera)` 没有传 `detailDistanceScale`；目前设置只调整车辆近景距离，沿路树仍使用原距离。这是可以先修的小范围问题。

将同一档位的预算传到通勤路侧树、校园植被、建筑细节、交通外观、室外事件和 C118；各模块保留自己的实际阈值，不强迫全部使用同一个距离。增加“各模块实际生效预算”诊断表，检查隐藏模块是否仍更新。

逐一验收自动/流畅/均衡/清晰、停在 LOD 边界、快速回头、导出全量及销毁重建。保持每棵树只显示一个 LOD，远处碰撞与蛛丝目标持续有效。此项预计 0.5–1 个开发日，依赖范围比街区重构小，应先交付。

**5．P1-1：室外海啸、洪水和透明效果分档**

涉及 `src/campus-floodwater.js`、`src/campus-tsunami.js`、`src/live-experience.js` 与 `src/survey.js`。现有洪水第一次使用时构建约 9 km ×10 km 的 180×160 网格，启动效果后保留；水面透明双面、禁用整体视锥剔除。两个波峰、泡沫和粒子仍是固定预算。33 ms 的更新间隔只是降低状态/uniform 更新频率，不代表 GPU 每秒只画 30 次。

实施顺序：先测无效果、迎面波峰、全屏水面和水下四个视角，再给三档单独配置几何、粒子和着色复杂度。试验固定世界坐标水面分块、近细远粗、包含波高的保守包围盒；低档削减泡沫层和高频噪声。评估解析波面梯度替代片元重复高度采样，以及经正反面验证后的薄面单 pass；不盲目给所有透明面改渲染顺序或深度写入。

验收：固定设备/DPR/位置/事件秒数，低档效果 GPU 增量争取下降 ≥40%；不支持 GPU timer 时以模块关闭对照的帧分布报告替代，并注明限制。波前和持续水流保持世界坐标，已经淹没的地面不能重新露出；水上、水下、背面、暂停、晚加入、重连和改画质的水位/活动时间必须一致。物理采样与视觉细分解耦。

**6．P1-2：让出生区先可玩，削掉构建中的长任务**

涉及 `src/survey.js`、`src/campus-3d.js`、`src/campus-landcover.js`、`src/vegetation.js` 及通勤场景构建。

当前 generator 只在若干模块之间 yield；地被裁切、植被模板或复杂地标内部仍可同步占用数百毫秒。下一步先拆“规划与碰撞”和“美术网格”，使完整基础地面、道路/桥层、门洞、可行走数据和全校粗轮廓先就绪，再完成韵苑出生区玩家所需外观，允许行走。远区装饰随后按预算补齐。

纯多边形裁切、采样和 TypedArray 几何计算可在剖析确认后交给 Worker；Three 对象、DOM、GPU 上传留主线程。对稳定地图考虑带源数据哈希的离线生成包，保留现有构造路径供导出/制作和回退使用。Worker 结果携带数据集代号，退出/重新导入时取消并拒收旧结果。

出生区和首个载具所需材质做小批次预编译/上传，不在首屏预热全校材质。项目 r180 已具有 `compileAsync`，但它只帮助着色器编译，不能保证所有几何或纹理上传都无卡顿。[Three.js 编译接口](https://threejs.org/docs/pages/WebGLRenderer.html)

验收：真实可操作时间相对校准基线下降 25–30%；CPU >50 ms 构建任务数量至少减半，参考设备的单片段目标 ≤100 ms，继续拆大项后再向 ≤50 ms 收敛。同时检查第一次飞行、第一次穿战衣和首次跨区，避免只是把卡顿从开场挪到操作中。细节出现前后地面高度、门洞、出生位置、蛛丝锚点 ID 不变。

**7．P1-3：街区细节有界驻留，保持完整远景**

当前大部分细节先全量生成，距离剔除仅缩小可绘制实例前缀。下一步原型采用约 128 米街区：先按道路/建筑语义调整边界，再以街区和材质分组。大楼跨格时避免重复生成，门户和关键地标不能被硬切开。

| 层级 | 驻留方式 |
| --- | --- |
| 逻辑层 | 轻量碰撞、桥层、道路、门洞、活动点与蛛丝语义始终可用 |
| 远景层 | 低模建筑轮廓、树带、远湖持续存在，保留高空导航感 |
| 近景层 | 附近街区完整窗框、路缘、停车细节、树冠和门面 |
| 预取层 | 按当前速度和方向准备邻区；先试 2–3 秒前向范围，再按内存预算约束 |
| 回收层 | 离开更远阈值并经过冷却后回收装饰资源；共用模板引用计数，避免连带释放 |

同材质不透明几何在区内合批，窗框、灯具、电动车优先实例化；保留源 feature ID、点击和导出映射。树簇先做保守空间块筛选，再执行已有每树 LOD，减少镜头移动时全量分类。纯色材质不必先做大图集；实际贴图和重复材质依据统计决定。

建议先只做“韵苑出生区—店廊”样板。通过后扩到 CBD、桥/东九、光电，不一次重写全校园。拟定门槛：典型视角绘制调用相对各自基线下降 ≥25%，流畅档细节属性缓冲驻留估算下降 ≥30%，密林分类 CPU 下降 ≥30%。拆分可能增加 draw calls，所以必须记录收益和负收益，不能以“已分区”代替通过。

连续跨边界 20 次、最高速度飞行穿越与回头、模型导出、上下车和进入 C118 均需验证。加载中保留粗模，不出现空楼、穿墙或突然无法挂丝；后台加载任务过期可取消。共享资源所有权验证通过后才启用真正卸载。

**8．P1-4：图书馆活动版资源重做预算**

| 已核实资产 | 首要处理 |
| --- | --- |
| `model.glb` 约 127.9 MB，94.15% 为几何，已有量化且未发现完全重复 bufferView | 先定位重网格、减面和分区，不把继续压图片当主方案 |
| 约 314 万个源网格索引三角形；按节点引用展开更多 | 源文件数量、展开数量、每帧可见数量分别记录 |
| `hero.glb` 约 25.8 MB，约 79.5% 是图像 | 第一人称延后角色；缩小贴图并评估 GPU 纹理压缩 |
| 图书馆 vendor 为 Three r170，校园为 r180 | 解码器与所属加载器版本配套；不能只替换为新压缩 GLB |

先去掉第一人称进入对完整 hero 的强制等待；可先用尺寸明确的轻量角色占位支撑必要逻辑，第三人称与剧情需要真实角色时再准备，不能改碰撞或剧情时机。主模型先针对最重前 10 个 mesh（约占源网格三角形的 41%）逐项制作 LOD，保留门、可交互书籍、命名节点、材质语义和动画绑定。

几何编码和几何简化分开试验：meshopt/Draco 主要评估传输与解码成本；真正减少面数需要有损简化及外观对照。不要一条全局 optimize 命令覆盖原作；固定楼梯/门口/书脊近景截图和交互清单，先做活动副本。[glTF Transform 简化说明](https://gltf-transform.dev/modules/functions/functions/simplify)

hero 的几张高分辨率贴图值得优先压缩。若按其 2 张 4096²、2 张 2048²、2 张 1024² 贴图全部作为 RGBA8 加完整 mip 估算，约 224 MiB；这是理论预算，不是实际显存。试验关键部位 2K、次要部位 1K，并按纹理语义评估 KTX2/Basis。补齐白名单内的解码器、Worker、MIME、缓存和失败回退；先 `detectSupport(renderer)`，低配限制转码并发，不能依赖临时外网 CDN。[KTX2Loader 官方说明](https://threejs.org/docs/pages/KTX2Loader.html)

拟定验收：图书馆轻量版首开可操作时间比当前同设备降低 ≥30%，活动版装饰几何减少 40–60%作为试验区间；hero 纹理驻留估算降低 ≥60%。达不到外观/交互标准时退回较高档，不能强行达到面数百分比。原生日项目、原通关判定和存档保留。

**9．P1-5：晚言制作真正的移动质量包**

当前 `.data` 约 103.4 MB、`.wasm` 约 42.6 MB；原构建来源记录 Unity `6000.6.0f1`、`qualityProfile: PC`、`textureSubtarget: Generic`。已有移动 DPR、触控和退出清理继续保留，但不能将它们当作移动渲染资产已完成。

先核对原 Unity 工程、版本、可重现构建和活动副本，借 Build Report 找纹理、音频、材质、阴影和场景引用热点，再生成桌面/移动两个受控资源档。优先减少移动阴影、后处理、无关着色器变体和过大纹理；按目标浏览器验证纹理格式及回退。只有源码/构建链可用时才调整 Unity 内存和资源加载组织，不直接篡改编译后的 data/wasm 容器。

第一步先不拆成复杂按场景流式加载；若首包仍过大再评估分包工程，不能承诺网页 loader 一改就能增量加载整个 Unity data。验收分开计下载、解压、wasm 编译、引擎初始化和第一帧；移动机实际进入战斗、旋转视角、普攻/技能/就绪提示及返回，真实胜利事件和存档不得回归。

没有可重现 Unity 工程时，本项明确记为构建前置条件缺失；继续完成网页生命周期、资源缓存和真机测量，不编造移动重构包。

**10．P1-6：C118 与多运行时内存、渲染节奏**

C118 水体分档、NPC 降频、局部矩阵上传和实例释放已经完成。下一步针对透明水体片元、远排人物、视频解码和持续高刷运行做分项对照。

静坐看大屏时试验按新视频帧/必要交互事件或上限 30 Hz 重绘；行走、环视和演出按设备档位提高频率。校园普通设备可提供 60 Hz 绘制上限，手机以稳定 30 Hz 为候选策略；输入采样、固定步长物理和活动时钟不随之降精度。现有质量控制必须收到正确 `targetFrameMs`，避免把主动 30 Hz 当作掉帧不断降画质。移动优先级高于装饰更新。

校园→图书馆→书中 Unity 可能同时保留三套 WebGL 运行时。先量峰值：隐藏/暂停只减少工作，不释放 GPU 资源。若低内存设备确认超预算，优先释放校园近景装饰；图书馆进入书中游戏时考虑只保留轻量逻辑和返回快照，再按区恢复。不要直接强制丢失校园上下文，或把几百 MB 重下载放到每次返回。

复查 C118 初始化中途失败、模型解析失败、视频错误、加载中退出、恢复失败和 BFCache。正常进出 20 轮，并记录仍存活的渲染器、媒体、音频、Worker 和事件订阅。已有三个作品各 10 轮返回验证继续复用为功能回归；新的任务是增加内存、音频和真机数据，不重复将 iframe 数为零当作内存证明。

**11．P1-7：服务端先减少 COUNT/心跳，再讨论新增服务**

上一轮隔离长测共 88,727 次 SQL，其中公共状态读取 4,491 次、COUNT 33,587 次、写入 26,035 次。公共状态已做缓存，因此下一轮主要检查每条 SSE 的在线计数/续租、每标签心跳，以及后台统计刷新，而不是再次宣称优化公共状态缓存即可解决全部成本。

部署仓库重点：`serverless/activity-api.mjs`、`src/audience-client.js`、`src/live-client.js`。先识别消费者，把仅用于校时的事件收敛为时间信号；在线展示允许使用明确的低频聚合，但认证、入场限制、CAS 和探索事件仍以实时服务端校验为准。心跳和连接轮换加随机错峰，保持当前连接上限和掉线 TTL；多标签共享连接可做局部试验，但要有领导标签关闭/后台被冻结时的接管，不把它算成不同观众共享一条连接。

主目录的本地 Node/JSON 存储是另一条实现：复查每次心跳复制和写整份 JSON 的成本，可以合并非关键在线状态写入，但已确认的到访/打开/返回事件必须可靠保存。不要把 Vercel SQL 缓存代码直接复制进本地服务。

长测脚本补响应体中断、请求关联号、SQL/事件循环耗时和慢消费者诊断；每次主持修改必须确认所有当时活跃观众在期限内收到相应或更新 revision，不只看总体 P95。首轮 19 分钟 HTTP 失败仍未定位，第二轮通过不能证明原因已修复。

先在 Node 24、隔离数据库、两个实例重做 100 人 30–60 分钟，加入全体同秒进入、240 秒轮换、断网和数据库短暂故障。拟定 COUNT 查询下降 ≥80%、总 SQL 下降 ≥25%，同时主持 P95 不超过 3 秒、身份/记录/离线判断不退化。再用隔离远程数据库验证真实网络；不在生产场次造 100 个观众记录。买新消息服务或更大服务器前，先拿查询量、函数耗时和带宽实测判断。

**12．缓存、弱网与多人同时进入作品**

现站大资源已返回 Brotli；不重复做“新增 gzip”作为主要成果。大模型稳定路径当前约 1 小时缓存，不能直接改成一年 immutable；先为模型、解码器和 Unity 构建建立内容版本路径，再配置长期缓存，HTML 与入口清单及时更新。验证旧页面和新 manifest 不混用、ETag/Range/304/206、iframe 路由以及回滚后的资源保留。

用实际完整请求测传输体积，分别验证 10 Mbps/较高延迟的受控网络和现场 Wi-Fi。50 MB 实际压缩传输在 10 Mbps 的理想下限约 40 秒，因此不能只优化加载提示而承诺数秒打开。校园首屏继续不请求三个重作品；预热只针对主持人下一步明确的单个作品，并受设备与网络预算约束，退出可取消。

5–10 台真实设备同时冷加载，记录可操作时间分布、失败率和现场出口带宽，再决定错峰开放或活动前预热。降低客户端帧成本和改善多人下载是两条独立验收线。当前公开访问证据不能替代现场无代理可用性检查。
